## 一、项目概述

### 1.1 项目背景

"快乐羊毛"旨在打造一个综合性优惠生活服务平台，通过整合第三方电商、本地生活服务（外卖、餐饮、打车、电影）及虚拟充值资源，为用户提供省钱优惠。同时平台构建了一套分佣体系，支持代理商和分销员参与推广，实现流量变现。

**与旧系统"今夜到家"的关系**：快乐羊毛是在今夜到家系统基础上的全新项目。今夜到家是到家服务平台（技师上门服务），快乐羊毛则转型为综合优惠生活服务平台。两者共用部分基础架构和分佣逻辑，但业务模式完全不同。

### 1.2 产品目标

| 端 | 目标 |
|----|------|
| **用户端** | 提供一站式省钱工具，涵盖餐饮、外卖、出行、购物等高频场景 |
| **商户端** | 为连锁品牌提供私域流量运营工具，实现会员共享与核销管理 |
| **管理端** | 高效管理商品、订单、分佣及财务结算，支持多渠道API对接 |

### 1.5 三大核心业务模式

| 模式 | 资金流向 | 数据流向 | 适用场景 |
|------|---------|---------|---------|
| **CPS跳转类** | 用户在第三方平台支付，不经过本平台 | 第三方回传数据或运营手动补录 → 计算分佣 | 外卖红包、打车、家电购物、连锁品牌直跳、加油/充电 |
| **平台交易类** | 用户在本平台支付 → 平台收银 → 对接第三方API下单/发货 | 第三方结算佣金给平台 → 平台分发分佣 | 通用券、会员充值、电影票 |

## 二、用户端功能需求（微信小程序）

### 2.1 免费资料区

#### 2.1.1 功能描述
展示各类电子档资源（行业报告、学习资料、教程等），纯内容展示模块，无交易闭环。

#### 2.1.2 页面逻辑
- **列表页**：展示资料标题、简介、更新时间，按更新时间倒序排列
- **详情页**：展示资料完整信息及多个资源链接
- **分页**：每页10条，滚动到底部触发加载更多，最后一页显示"没有更多了"
- **分类**：支持分类Tab筛选（如"学习资料""工具模板""行业报告"），支持"全部"分类

#### 2.1.3 交互规则
| 操作 | 行为 |
|------|------|
| 点击列表项 | 跳转详情页 |
| 点击"复制链接" | 复制链接到剪贴板 → 弹出"复制成功"Toast（2秒消失）→ 可跳转浏览器/App |
| 详情页返回 | 列表保持滑动位置和数据，不重新加载 |
| 列表为空 | 展示空状态占位图+"暂无资料"文案 |
| 某分类为空 | 展示"该分类暂无资料"文案 |

#### 2.1.4 后台管理
- 支持资料增删改查
- 支持分类管理
- 接口需求：无（纯CMS内容管理）

**测试关注点**：
- 验证分页加载的数据连续性，无重复/遗漏
- 快速切换分类Tab时，数据请求是否存在竞态条件
- 详情页返回后列表位置恢复的准确性
- 复制链接功能在不同机型上的兼容性

### 2.2 外卖区

#### 2.2.1 红包（CPS跳转）

**功能描述**：用户点击对应平台红包Icon，通过中间页跳转至App领券页面。

**支持平台**（5个）：

| 平台 | Icon名称 | 跳转目标 |
|------|---------|---------|
| 美团 | 美团 | 美团App领券页 |
| 饿了么 | 饿了么 | 饿了么App领券页 |
| 淘宝 | 淘宝 | 淘宝App领券页 |
| 京东 | 京东 | 京东App领券页 |
| 美团拼好饭 | 美团拼好饭 | 美团App拼好饭领券页 |

**对接渠道**：美赚、聚推客、凡点（三选一）

**渠道选择策略**：
| 模式 | 说明 |
|------|------|
| **优选模式** | 自动选择佣金比例最高的渠道。例：美赚5%、聚推客8%、凡点6%→ 选聚推客 |
| **轮询模式** | 依次分配至三个渠道，保证均匀分配。30次请求→各渠道10次 |

**异常处理**：
| 异常场景 | 处理 |
|----------|------|
| 当前最优渠道不可用 | 自动降级至佣金次高的可用渠道 |
| 所有渠道均不可用 | 展示"当前服务繁忙，请稍后重试" |
| 渠道恢复后 | 自动恢复优选至该渠道 |
| 佣金比例变更后 | 优选结果实时更新 |
| 未安装目标App | 提示"未安装XX App"并引导下载，或降级打开H5页面 |
| 中间页加载超时 | 5秒超时后展示"加载失败，请重试"及重试按钮 |

**跳转流程**：
```
用户点击Icon → 中间页(加载参数+loading) → 跳转目标App领券页
                    ↓(超时5秒)
              "加载失败，请重试"
```

**测试关注点**：
- 优选模式下，多渠道佣金比例相同时的选择策略（是否有默认优先级）
- 轮询模式下，计数器重启/持久化机制（应用重启后是否重新计数）
- 渠道降级后恢复的自动检测频率
- 高并发场景下轮询分配的准确性

#### 2.2.2 通用券（平台交易）

**功能描述**：美团通用券，用户选择面额购买，平台通过API自动发放卡密/券码。

**商品信息**：
| 字段 | 说明 |
|------|------|
| 面额 | 如5元、10元、20元、50元 |
| 售价 | 如9.5元（购买10元面额券） |
| 渠道 | 蜂助手、骑士 |

**购买流程**：
```
选择面额 → 确认订单(显示红色"支付后不退款"提示)
         → 勾选"已阅读并同意"协议(未勾选不可支付)
         → 微信支付 → 支付成功
         → 系统调API下发卡密(DELIVERING)
         → 卡密下发成功(COMPLETED，展示卡密+有效期)
```

**订单详情页展示**（支付成功后）：
- 展示：卡密号码、券码、有效期
- 操作按钮：复制卡密、复制券码、再次购买、查看详情、联系客服
- **不展示**：申请退款按钮
- 有效期即将到期：有效期文字标红，附"即将过期"标签

**发货失败处理**：
```
支付成功 → API调用失败(FAIL) → 用户端显示"发货失败"
                              → 运营后台显示"重试发货"和"退款"按钮
                              → 重试成功 → COMPLETED
                              → 退款 → REFUNDED(原路退回)
```

**异常场景**：
| 场景 | 处理 |
|------|------|
| 未选面额点击购买 | 提示"请先选择面额" |
| 支付超时(5分钟) | 支付弹窗关闭，提示"支付超时，请重新下单"，订单已取消 |
| 库存为0 | 显示"已售罄"，购买按钮置灰 |
| 支付中断网 | 提示网络异常，恢复后订单为"待支付"或"已取消"，不会扣款无卡密 |
| 切换面额 | 前一个取消高亮，新选面额高亮，显示对应售价 |
| 同一面额重复点击 | 取消选中状态（toggle行为），需确认产品设计 |
| 支付成功但API回调延迟 | 用户端显示"处理中"loading，轮询查询订单状态 |

**测试关注点**：
- 支付金额防篡改：前端传递的金额与后端订单金额一致性校验
- 支付成功后API调用失败时，重试发货的幂等性（不会重复发放卡密）
- 卡密展示的安全性（是否需要点击"查看"才显示完整卡密）
- 有效期即将过期的判定阈值（距到期多少天标红）

### 2.3 餐饮折扣（核心复杂模块）

#### 2.3.1 连锁品牌直跳（CPS模式）

**适用对象**：麦当劳、肯德基、星巴克等大型连锁品牌

**功能描述**：纯流量分发，无交易闭环。平台展示品牌信息，用户点击跳转到品牌官方页面完成消费。

**展示要素**：
| 要素 | 说明 |
|------|------|
| 品牌Logo | 清晰无变形 |
| 品牌名称 | 正确显示 |
| 优惠Banner | 当季活动，如"麦当劳随心配1+1仅12.9元" |

**跳转方式**：
| 方式 | 说明 |
|------|------|
| 小程序跳转 | 跳转品牌官方小程序对应优惠页 |
| H5跳转 | 在内嵌浏览器打开品牌H5优惠页 |

**CPS参数**：跳转链接携带渠道参数（如channel=klym_2026），确保佣金可追踪。

**对接渠道**：
| 渠道 | 接入方式 | 说明 |
|------|---------|------|
| 趣满满 | H5接入 | PRD v1指定渠道，通过H5接入获取收益，无需人工干预 |
| 骑士 | API | V2.0补充渠道 |
| 凡点 | API | V2.0补充渠道 |

> **差异说明**：PRD v1中餐饮折扣品牌直跳对接渠道为"趣满满"（H5接入模式），V2.0文档中改为"骑士、凡点"。需与产品/开发确认最终渠道方案，可能存在多渠道并行的情况。

**异常处理**：
| 场景 | 处理 |
|------|------|
| 跳转链接失效 | 提示"该品牌优惠暂不可用，请稍后再试" |
| 未配置品牌 | 展示空状态+"暂无品牌优惠" |
| H5页面加载失败 | 展示"页面加载失败"及重试按钮 |
| 品牌活动已过期 | 后台标记过期后前端不展示，若缓存导致仍展示则点击后提示 |

#### 2.3.2 品牌会员共享 — 模式一：系统直连

**适用对象**：有收银系统、愿意配合接入平台或使用平台收银工具的品牌。

**核心流程**：

```
商家输入消费原价(如100元)
    ↓
系统自动计算折扣(8折→实付80元，优惠20元)
    ↓
商家可手动修正金额(需权限，仅品牌主账号)
    ↓
生成收款二维码
    ↓
用户微信扫码 → 支付确认页(原价100/优惠20/实付80)
    ↓
用户完成微信支付 → 资金进入平台账户
    ↓
订单状态"已支付" → 三端可见(用户端/商家端/后台)
```

**折扣计算规则**：
| 场景 | 原价 | 折扣率 | 实付 | 优惠 |
|------|------|--------|------|------|
| 正常 | 100元 | 8折 | 80.00元 | 20.00元 |
| 含小数 | 99元 | 8.5折 | 84.15元 | 14.85元 |
| 四舍五入 | 33元 | 8.5折 | 28.05元 | 4.95元 |
| 极小金额 | 0.01元 | 8折 | 0.01元 | 0.00元 |
| 折扣后为0 | 0.01元 | 1折 | 0.00元 | 需确认最低支付金额 |

**金额精度**：精确到分（小数点后两位），四舍五入。

**输入校验**：
| 输入 | 处理 |
|------|------|
| 0 | 提示"消费金额必须大于0" |
| 负数 | 不允许输入负号 |
| 超大金额(>50000) | 提示"单笔消费金额不能超过50000元" |
| 非数字 | 只允许数字和小数点 |
| 多个小数点 | 只允许一个小数点 |
| 小数点后超过2位 | 自动截断或限制输入 |
| 纯小数点 | 不允许提交 |

**二维码规则**：
- 二维码超时时间：15分钟
- 超时后扫码提示"该收款码已失效，请联系商家重新生成"
- 同一二维码不可被两人同时支付（并发控制）

**退款规则**（此模块保留退款功能）：
| 操作方 | 流程 |
|--------|------|
| 用户发起 | 订单详情→申请退款→选择退款原因→提交→状态变"退款中" |
| 商家发起 | 订单管理→退款→输入退款原因→确认→状态变"退款中" |
| 运营审核 | 审核通过→原路退回微信(1-3工作日)→订单状态"已退款" |

**部分退款**：支持。运营输入退款金额（不超过实付），如实付80退40→订单状态"部分退款"。

**退款校验**：
| 校验 | 处理 |
|------|------|
| 退款金额>实付金额 | 提示"退款金额不能超过实付金额80元" |
| 退款金额=0 | 提示"退款金额必须大于0" |
| 退款金额为负数 | 输入被拦截 |
| 重复退款 | 退款按钮置灰/隐藏 |
| 部分退款后再次退款 | 退款金额上限为剩余可退金额 |

**角色权限**：
| 角色 | 权限 |
|------|------|
| 品牌主账号 | 创建/管理子账号、查看全店数据、手动修正折扣 |
| 门店子账号 | 收银台操作、查看本店订单/数据、发起退款 |

**测试关注点**：
- 并发扫码：两人同时扫同一二维码的处理（第二人应提示"该订单已被支付"）
- 二维码15分钟超时的精确性
- 手动修正金额的权限控制（门店子账号是否确实无法修正）
- 退款到账时间与微信接口的一致性

#### 2.3.3 品牌会员共享 — 模式二：人工辅助/验证码模式（新增核心需求）

**适用对象**：无系统对接，可由代理商拓展的商家。通过"人工介入"方式覆盖无法系统直连的商家。

##### A. 基础设置（代理商/运营端）

**商户录入字段**：
| 字段 | 是否必填 | 校验规则 | 示例 |
|------|---------|---------|------|
| 商家名称 | 是 | 不能为空，建议限制长度 | 张三烤肉店 |
| 地址 | 是 | 不能为空 | 北京市朝阳区建国路88号 |
| 联系电话 | 是 | 11位手机号格式校验 | 13800138001 |
| 所属品牌 | 否 | — | 张三烤肉 |
| 折扣设置 | 是 | 1-9.9折范围校验 | 8.5折 |
| 会员充值账号 | 否 | — | zhangsan_vip |

**审核机制**：
```
代理商/运营录入商家信息 → 状态"待审核"
    ↓
平台运营审核:
  ├── 审核通过 → 状态"已通过" → 前端用户可见
  └── 审核驳回(填写理由) → 状态"已驳回" → 前端不展示
                                         → 代理商收到驳回通知
                                         → 可补充后重新提交
```

**测试关注点**：
- 折扣设置边界值：1折（最低）、9.9折（最高）、0.9折（低于下限）、10折（等于原价）
- 审核驳回后重新提交，是否保留原信息供修改
- 同名商家是否允许重复录入

##### B. 用户下单与凭证上传（用户端）

**完整交互流程**：
```
用户在"餐饮折扣"列表选择人工辅助模式商家
    ↓
点击"去买单" → 进入人工核销页
    ↓
输入消费总金额(原价，如100元)
    ↓
系统展示预计折扣(原价100，折后85，优惠15)
    ↓
上传凭证(拍摄小票/上传支付截图)
    ↓
点击"提交订单" → 状态"待审核(PENDING_AUDIT)"
```

**金额计算**：消费金额 × 折扣率 = 实付金额。如100 × 0.85 = 85元。

**凭证上传规则**：
| 规则 | 说明 |
|------|------|
| 支持格式 | JPG、PNG等图片格式 |
| 不支持格式 | PDF等非图片格式，提示"仅支持图片格式" |
| 大小限制 | 单张不超过10MB，超出提示"图片大小不能超过10MB" |
| 多图支持 | 支持上传多张凭证(小票+支付截图)，缩略图展示 |
| 数量限制 | 建议最多上传5张（需确认） |
| 预览 | 支持点击缩略图预览大图 |
| 删除 | 支持删除已上传的图片重新选择 |

**提交校验**：
| 校验项 | 未满足时提示 |
|--------|------------|
| 未输入金额 | "请输入消费总金额" |
| 金额为0或负数 | "消费金额必须大于0" |
| 金额超过上限 | "单笔消费金额不能超过50000元"（需确认） |
| 未上传凭证 | "请上传消费凭证（小票照片或支付截图）" |

##### C. 运营审核与验证码下发（运营后台）

**审核列表**：
- 展示所有待审核订单：用户信息、商家名称、消费金额、提交时间、凭证缩略图
- 支持按状态筛选（待审核/已通过/已驳回）
- 点击订单进入审核详情，凭证照片可放大查看

**审核操作**：
```
运营查看订单照片和金额
    ├── 驳回(必须填写驳回理由)
    │     → 用户收到通知(订阅消息/短信)
    │     → 用户可重新上传凭证再次提交
    │
    └── 通过
          → 联系商家获取验证码
          → 在订单详情页输入验证码(不能为空)
          → 点击"确认下发"
          → 系统自动向用户推送验证码
          → 订单状态变为"验证码已下发"/"已完成"
```

**防重复审核**：审核通过/驳回后，操作按钮置灰不可点。

**测试关注点**：
- 驳回理由为空时的提交拦截
- 验证码为空时点击"确认下发"的拦截
- 审核通过后是否不可修改为驳回（状态不可逆）
- 多运营人员同时审核同一订单的并发处理

##### D. 验证码回传与核销

**验证码推送方式**（按优先级）：
| 优先级 | 方式 | 条件 |
|--------|------|------|
| 1 | 小程序订阅消息 | 用户已授权订阅消息 |
| 2 | 短信 | 用户未授权订阅消息 |
| 3 | 订单详情页查看 | 兜底方案（两种方式均失败时） |

**推送内容**：包含验证码、商家名称、消费金额。推送时效：<1分钟。

**推送失败处理**：两种方式均失败时，运营端提示"验证码发送失败，请通过其他方式通知用户"，验证码仍可在用户订单详情页查看。

**线下核销流程**：
```
用户到店 → 展示/口述验证码给收银员
    ↓
商家在商家端输入验证码 → 点击"确认核销"
    ├── 验证码正确 → 核销成功 → 订单状态"已完成"
    ├── 验证码错误 → 提示"验证码错误，请重新输入"
    └── 验证码过期(超48小时) → 提示"验证码已过期，请联系平台客服"
```

**验证码安全规则**：
| 规则 | 说明 |
|------|------|
| 唯一性 | 每个订单验证码唯一 |
| 防重复使用 | 已核销的验证码不能再次使用 |
| 有效期 | 48小时（需确认） |
| 防暴力破解 | 连续5次输错后锁定15分钟 |
| 格式 | 需确认验证码格式（纯数字？位数？） |

##### E. 分佣计算
订单完成后，系统根据"订单原价"和"设置好的分佣比例"自动计算代理商和分销员的佣金收益。**即使资金未经过平台，也基于交易流水产生服务费/佣金**。

### 4.5 分佣系统（核心模块）

#### 4.5.0 分佣是什么？（通俗解读）

> 为了便于理解，先用大白话解释分佣的本质。

**一句话概括**：用户在平台消费后，平台从中赚到的利润，按约定比例分给帮忙推广的人。

**举个生活化的例子**：
```
假设你开了一个优惠券平台：
- 用户花85元买了一张餐饮折扣券
- 这张券的成本是50元（你需要付给商家的）
- 你赚的利润 = 85 - 50 = 35元

这35元利润怎么分？
- 平台自己留一部分（运营费用）
- 帮你推广的代理商拿一部分（他负责在当地推广你的平台）
- 帮代理商拉用户的分销员拿一部分（他把用户推荐过来的）

这就是分佣。
```

**核心逻辑（3条记住就行）**：
1. **只分利润，不分成本** — 成本部分谁都拿不到，先扣除
2. **三方分钱：平台 + 代理商 + 分销员** — 这是快乐羊毛的分佣对象
3. **分销员的钱从代理商那里扣** — 分销员拿多少，代理商就少拿多少，不影响平台

---

#### 4.5.1 分佣参与方（快乐羊毛）

> 以下为PRD v1明确定义的快乐羊毛分佣角色，共3方。

| 角色 | 是谁？ | 怎么分？ | 后台配置 |
|------|--------|---------|---------|
| **平台** | 快乐羊毛平台自己 | 从利润中按比例抽取 | 后台设置平台分佣比例 |
| **代理商** | 负责某个区域推广的合作方（如"重庆区域代理"） | 从利润中按比例抽取 | 后台设置代理商分佣比例 |
| **分销员（一级）** | 被代理商发展的推广人员，负责邀请用户来消费 | 从**代理商的份额中**按比例扣除 | 代理商自行设置分销员比例 |
| **分销员（二级）** | 被一级分销员发展的下级推广人员 | 从**代理商的份额中**按比例扣除 | 代理商自行设置分销员比例 |

**关系图**：
```
          用户消费产生订单
               ↓
         订单金额 - 成本 = 利润
               ↓
     ┌─────────┴─────────┐
     ↓                   ↓
   平台(X%)         代理商(Y%)        ← X% + Y% = 100%，利润全部分完
                         │
                   ┌─────┴─────┐
                   ↓           ↓
               一级分销员   二级分销员   ← 从代理商的Y%里扣
               (从代理商    (从代理商
                份额扣)     份额扣)
```

**重要规则**：
- **平台 + 代理商 = 100%**，利润全部分完，没有剩余
- 分销员的佣金是从代理商份额中扣的，**不是额外多分**
- 代理商实际到手 = 代理商份额 - 一级分销员佣金 - 二级分销员佣金
- 如果没有分销员推荐，代理商拿全部代理商份额
- **快乐羊毛没有渠道员和业务员**（只有今夜到家才有）

---

#### 4.5.2 核心分佣规则

**第一步：算利润**
```
利润 = 用户实际支付金额 - 投入成本（后台设置的原价/进货价）
```
- **后台有"原价"字段**：每个商品/服务在后台设置了一个原价（即成本/进货价），用于计算利润
- 如果有优惠券，先扣掉优惠券金额
- 如果有成本（后台设置的原价），先扣掉成本
- 剩下的才是可以分的"利润"

**原价的作用**：原价 = 平台的成本，用户实付金额 - 原价 = 利润（平台的毛利润），分佣只分这个利润

**第二步：按比例分给各方**

| 计算项 | 公式 | 说明 |
|--------|------|------|
| 利润 | 实付金额 - 投入成本（后台原价） | 可分配的总金额 |
| 平台佣金 | 利润 × 平台比例 | 平台拿走的部分 |
| 代理商佣金 | 利润 × 代理商比例 | 代理商应得的总份额 |
| 一级分销员佣金 | 利润 × 一级分销员比例 | **从代理商佣金中扣除** |
| 二级分销员佣金 | 利润 × 二级分销员比例 | **从代理商佣金中扣除** |
| 代理商实得 | 代理商佣金 - 一级分销员佣金 - 二级分销员佣金 | 代理商实际到手 |

**约束**：
- **平台比例 + 代理商比例 = 100%**（已确认：利润全部分完，没有剩余）
- 分销员比例从代理商份额中扣，一级+二级不能超过代理商比例
- **快乐羊毛只有这3方（平台、代理商、分销员），没有渠道员和业务员**

#### 4.5.3 分佣计算示例

**示例一：最简单场景（只有平台和代理商，没有分销员）**
```
场景：用户自己搜到平台来消费，没有任何人推荐

订单实付: 100元
投入成本: 60元（后台设置的原价/进货价）
利润: 100 - 60 = 40元

假设：平台比例50%，代理商比例50%（合计100%）

平台拿:   40 × 50% = 20.00元
代理商拿: 40 × 50% = 20.00元
合计: 20 + 20 = 40元 = 利润 ← 全部分完，没有剩余

结果：平台20元，代理商20元
```

**示例二：有一级分销员推荐用户**
```
场景：分销员小张邀请用户来消费

订单实付: 100元
投入成本: 60元
利润: 40元

假设：平台50%，代理商50%，一级分销员10%

平台拿:       40 × 50% = 20.00元
代理商份额:    40 × 50% = 20.00元
一级分销员拿:  40 × 10% = 4.00元（从代理商的20元中扣）
代理商实际到手: 20.00 - 4.00 = 16.00元

结果：平台20元，代理商16元，分销员小张4元
验证：20 + 16 + 4 = 40元 = 利润 ✓
```

**示例三：有一级+二级分销员**
```
场景：一级分销员小张邀请了二级分销员小李，小李又邀请了用户来消费

订单实付: 100元
投入成本: 60元
利润: 40元

假设：平台50%，代理商50%，一级分销员10%，二级分销员5%

平台拿:        40 × 50% = 20.00元
代理商份额:     40 × 50% = 20.00元
一级分销员小张: 40 × 10% = 4.00元（从代理商扣）
二级分销员小李: 40 × 5%  = 2.00元（从代理商扣）
代理商实际到手: 20.00 - 4.00 - 2.00 = 14.00元

结果：平台20元，代理商14元，小张4元，小李2元
验证：20 + 14 + 4 + 2 = 40元 = 利润 ✓
```

**示例四：餐饮折扣场景（人工辅助模式）**
```
场景：用户在商家消费100元，折扣8.5折
特殊点：资金没有经过平台，但仍然按交易流水计算分佣

消费原价: 100元
折后价: 85元（用户实付）
优惠金额: 15元

分佣基数 = 按原价和折扣差额计算（具体以系统设置为准）
```

#### 4.5.4 不同业务线的分佣方式

> 不同业务的"利润"来源不一样，所以分佣方式也不同。

| 业务线 | 利润从哪来？ | 谁来算？ | 举例 |
|--------|------------|---------|------|
| **餐饮折扣(扫码支付)** | 用户实付金额 - 商家结算金额 = 平台利润 | 系统自动算 | 用户付80，平台给商家65，利润15元 |
| **餐饮折扣(人工辅助)** | 基于订单原价和折扣差额 | 系统自动算 | 即使钱没过平台，也按流水算分佣 |
| **虚拟商品(券/充值)** | 第三方API返回的佣金 | API回传 | 骑士给平台返佣5元，这5元就是可分配的 |
| **CPS跳转类(外卖红包/打车/家电)** | 第三方平台结算的推广佣金 | 运营手动导入Excel | 导入的佣金直接就是佣金，不需要再扣成本，直接按比例分给各方 |
| **购物返利** | 联盟订单的推广佣金 | 定期同步 | 淘宝联盟每月结算佣金，系统同步后分配 |

#### 4.5.5 Excel佣金导入

**适用场景**：CPS跳转类业务（外卖红包、打车、家电等），第三方渠道不提供API回调佣金数据时，运营人员手动导入。

**模板字段**：用户ID、订单金额、佣金金额

**导入校验**：
| 异常 | 处理 |
|------|------|
| 空文件 | 提示"文件无数据" |
| 缺必填列 | 提示"缺少必要字段：佣金" |
| 用户ID不存在 | 该行标记失败并跳过，其他行正常 |
| 佣金为负数 | 该行标记失败 |
| 佣金为0 | 需确认是否允许（0佣金记录是否有意义） |
| 佣金大于订单金额 | 该行标记失败（佣金不应超过订单金额） |
| 非Excel格式 | 提示"请上传Excel格式文件" |
| 重复导入 | 提示已存在，给出处理选项（覆盖/跳过/取消） |
| 超大文件 | 需确认文件大小和行数限制 |

#### 4.5.6 结算管理

**通俗说明**：分佣算出来后，钱不是立刻就能提现，要经过一个"冷却期"（结算周期），确认订单没问题后才能提现。

**结算流程**：
```
订单完成
    ↓
佣金进入"待结算"状态（还不能提现）
    ↓ (等待结算周期，如T+7或T+15，待确认)
佣金变为"可提现"状态
    ↓
分销员/代理商在个人中心申请提现
    ↓
运营审核
    ├── 通过 → 打款到微信 → 余额扣减
    └── 拒绝 → 退回可提现状态（附拒绝原因）
```

**提现校验**：
| 校验 | 处理 |
|------|------|
| 提现金额>可提现余额 | 提示"提现金额不能超过可提现余额XX元" |
| 提现金额≤0 | 提示"提现金额必须大于0" |
| 待结算金额为0 | 无法提现 |
| 最低提现金额 | 需确认是否有最低提现门槛 |
| 提现手续费 | 需确认是否收取手续费 |

#### 4.5.7 退款对分佣的影响

| 场景 | 处理 | 举例 |
|------|------|------|
| 全额退款 | 各角色佣金记录增加冲抵记录(-XX元)，可提现余额减少 | 订单退款，平台佣金-3.20，代理商佣金-16.80 |
| 部分退款 | 利润重新计算，各角色佣金按新利润调整，差额从待结算扣除 | 实付100退了40，利润变小，佣金相应减少 |
| 佣金已提现后退款 | 产生欠款记录，从下笔佣金扣除 | 代理商已提走16.80，订单退款后，下笔佣金中扣回 |

**测试关注点**：
- 退款后分佣冲抵的计算准确性
- 佣金已提现后退款的欠款追溯机制
- 多级分销场景下退款的连锁冲抵（一级+二级分销员的佣金都要冲抵）
- 结算周期的准确性

#### 4.5.8 分佣边界情况

| 场景 | 处理 |
|------|------|
| 利润为0(投入=实付) | 所有角色佣金均为0.00元 |
| 利润为小数(37.20元) | 佣金精确到分，如37.20×10%=3.72元 |
| 极小利润(0.01元) | 佣金四舍五入可能为0.00元，不产生负数 |
| 利润为负(投入>实付) | 不应出现此场景，需后端校验拦截 |
| 比例总和>100% | 保存失败，提示"分佣比例总和不能超过100%" |
| 比例为负数 | 输入被拦截 |
| 比例>100% | 提示"比例不能超过100%" |
| 比例为0% | 允许（该角色不参与分佣） |
| 比例包含小数(如8.5%) | 允许，精度需确认（小数点后几位） |
| 分销员佣金之和>代理商份额 | 应拦截，提示"分销员分佣比例不能超过代理商比例" |
| 代理商未设置分销比例 | 分销员佣金为0，代理商获得全部代理商份额 |
| 订单没有绑定代理商 | 需确认：是否必须有代理商？XMind中标注"必须有代理商" |
| 平台+代理商比例不等于100% | 后台应拦截，提示"平台和代理商比例之和必须等于100%" |

#### 4.5.9 今夜到家分佣体系参照（来源XMind）

> 快乐羊毛的分佣参照今夜到家的架构，大体逻辑一致。以下为今夜到家的完整分佣体系，供理解分佣逻辑和测试时参考。**快乐羊毛只有平台、代理商、分销员三方，不含技师、经纪人、渠道员、业务员。**

**今夜到家分佣角色（5+方）**：

| 角色 | 比例 | 说明 |
|------|------|------|
| 技师 | 50% | 提供上门服务的人（**快乐羊毛无此角色**） |
| 平台 | 8% | 平台自留 |
| 代理商 | 42% | 区域运营 |
| 分销员(1级/2级) | 从代理商扣 | 推广获佣 |
| 渠道员 | 从代理商扣 | 今夜到家有，**快乐羊毛无此角色** |
| 业务员 | 从代理商扣 | 今夜到家有，**快乐羊毛无此角色** |
| 经纪人 | 从代理商扣 | 邀请技师加入获佣（**快乐羊毛无此角色**） |

**今夜到家vs快乐羊毛对比**：

| 对比项 | 今夜到家 | 快乐羊毛 |
|--------|---------|---------|
| 技师分佣 | 有（50%） | **无**（无技师角色） |

| 业务员 | 有 | **无**（已确认） |
| 经纪人 | 有（邀请技师） | **无** |
| 物料费 | 先扣除归平台 | 无物料费概念 |
| 车费补贴 | 平台/代理商补贴 | 无车费概念 |
| 手动录入佣金 | 无 | 有（Excel导入） |

**今夜到家渠道员规则（仅今夜到家有，快乐羊毛无此角色，仅供参考）**：
- 时效内+不换绑：绑定的渠道商参与分佣

#### 4.5.5 结算管理

**结算流程**：
```
订单完成 → 佣金"待结算"
    ↓ (结算周期到达)
佣金"可提现"
    ↓
分销员/代理商申请提现
    ↓
运营审核 → 通过 → 打款到微信 → 余额扣减
         → 拒绝 → 退回可提现状态
```

**提现校验**：
| 校验 | 处理 |
|------|------|
| 提现金额>可提现余额 | 提示"提现金额不能超过可提现余额XX元" |
| 提现金额≤0 | 提示"提现金额必须大于0" |
| 待结算金额为0 | 无法提现 |
| 最低提现金额 | 需确认是否有最低提现门槛 |
| 提现手续费 | 需确认是否收取手续费 |

#### 4.5.6 退款对分佣的影响

| 场景 | 处理 |
|------|------|
| 全额退款 | 各角色佣金记录增加冲抵记录(-XX元)，可提现余额减少 |
| 部分退款 | 利润重新计算，各角色佣金按新利润调整，差额从待结算扣除 |
| 佣金已提现后退款 | 产生欠款记录，从下笔佣金扣除 |

**测试关注点**：
- 退款后分佣冲抵的计算准确性
- 佣金已提现后退款的欠款追溯机制
- 多级分销场景下退款的连锁冲抵
- 结算周期的准确性

#### 4.5.7 今夜到家分佣体系参照（来源XMind）

> 快乐羊毛的分佣体系参照今夜到家的架构设计，核心逻辑大体一致。以下为今夜到家的完整分佣规则，快乐羊毛在此基础上根据新业务场景做适配调整。

**1. 今夜到家基础分佣结构**：
- 平台：8%（可自行设置）
- 代理商：42%（可自行设置）
- 剩余50%：今夜到家中归技师，快乐羊毛中无技师角色，此部分为成本/投入部分

**2. 分佣前置扣除规则（快乐羊毛沿用）**：
- 订单产生后，需优先扣除成本/优惠券金额
- 扣除后的利润部分才进入分佣计算
- 今夜到家中物料费统一归平台，再由财务结算给代理商

**3. 各角色分佣扣除关系（快乐羊毛沿用）**：
- 分销员（1级、2级）：从代理商份额中扣除
- 渠道员：从代理商份额中扣除
- 业务员：从代理商份额中扣除
- 以上角色的佣金均不影响平台份额

**4. 渠道员时效+换绑机制（仅今夜到家有，快乐羊毛无此角色）**：
- 时效内+不换绑：绑定的渠道商参与分佣
- 时效内+换绑：换绑后的渠道商参与分佣
- 时效外+不换绑：渠道商不分佣
- 时效外+换绑：渠道商不分佣

**5. 今夜到家分佣计算示例（供理解分佣逻辑参考）**：
```
订单：168元服务费 + 10元物料费 = 178元总价
① 物料费10元先扣除（归平台）
② 服务费168元参与分佣：
   - 50%（今夜到家中归技师，快乐羊毛中为成本/投入部分）
   - 平台：按设置比例分佣
   - 代理商：按设置比例分佣
③ 若有分销员/业务员/渠道员，其佣金从代理商份额中扣除
```

**6. 快乐羊毛适配要点**：

| 今夜到家原有 | 快乐羊毛适配 |
|-------------|-------------|
| 技师50% | 无技师角色，此部分变为投入成本，不参与分佣 |
| 平台8%+代理商42% | 保留，具体比例可配置 |
| 分销员从代理商扣除 | 保留此机制 |
| 渠道员/业务员 | **无**（已确认快乐羊毛没有这两个角色） |
| 经纪人（邀请技师） | 无技师角色，此角色不适用 |
| 物料费归平台 | 无物料费概念，但成本扣除逻辑保留 |
| 车费补贴 | 无车费概念 |

> **测试启示**：核心需验证"下级角色佣金从代理商份额扣除"这一机制的准确性，以及代理商可自行设置分销比例的功能。

### 5.1 订单状态编码对照表

> **V3.0补充**：PRD v1中提到当前订单状态机编码为 -1、1、2、3、4、5、6、7、8，以下为新系统的状态设计

| 状态编码 | 状态名称 | 枚举值 | 描述 |
|---------|---------|--------|------|
| 1 | 待支付 | WAIT_PAY | 订单创建，等待用户付款 |
| 12 | 待审核 | PENDING_AUDIT | 人工辅助模式，用户已上传凭证等待运营审核 |
| — | 发货中 | DELIVERING | 系统正在处理发货（请求第三方接口） |
| 7 | 已完成 | COMPLETED | 发货/核销成功，订单结束 |
| 11 | 失败 | FAIL | 发货/充值失败 |

### 5.2 虚拟商品类（外卖券/充值/电影票）

```
WAIT_PAY(待支付) ──超时──→ 已关闭
    │
    │ 支付成功
    ↓
DELIVERING(发货中) ──发货成功──→ COMPLETED(已完成) ★不可退款
    │
    │ 发货失败
    ↓
FAIL(失败) ──重试成功──→ COMPLETED
    │
    │ 退款
    ↓
REFUNDED(已退款)
```

### 5.3 餐饮折扣类（扫码支付-模式一）

```
WAIT_PAY(待支付) → 支付成功 → COMPLETED(已完成) ★保留退款
    │                                │
    │ 超时                            │ 退款
    ↓                                ↓
  已关闭                          REFUNDED(已退款)
```

### 5.4 餐饮折扣类（人工辅助-模式二）

```
WAIT_PAY(待支付-未使用,可选)
    ↓
PENDING_AUDIT(待审核) ──驳回──→ 用户重新上传 → PENDING_AUDIT
    │
    │ 通过+输入验证码
    ↓
COMPLETED(已完成/验证码已下发)
```

## 十二、术语表

| 术语 | 说明 |
|------|------|
| CPS | Cost Per Sale，按销售计费的推广模式 |
| 卡密 | 卡号+密码，虚拟商品兑换凭证 |
| 选品仓库 | 从第三方API同步商品到本地数据库的管理模块 |
| OSS | 阿里云对象存储服务，用于存储图片/视频资源 |
| 转链 | 将普通商品链接转为含推广参数的专属链接 |
| 核销 | 商家确认用户消费凭证的过程 |
| 分佣 | 订单利润按比例分配给各参与角色 |
| 投入部分 | 订单中的成本部分，不参与分佣计算 |
| type_id | 商品类型标识，用于接口区分和分佣规则匹配（1=骑士, 2=共享会员, 3=电影） |
| 渠道员 | 今夜到家的角色（有时效和换绑机制），**快乐羊毛没有此角色** |
