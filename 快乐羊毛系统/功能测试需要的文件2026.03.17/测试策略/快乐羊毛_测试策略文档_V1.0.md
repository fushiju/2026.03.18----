## 四、按模块测试策略详细方案

### 4.1 分佣系统（最高优先级）

**为什么是最高优先级**：涉及资金分配，计算错误直接造成经济损失。

#### 分佣计算测试矩阵

| 场景 | 测试数据 | 预期结果 |
|------|---------|---------|
| 无分销员 | 实付100，成本60，平台50%，代理商50% | 平台20.00，代理商20.00 |
| 有一级分销员 | 同上+一级10% | 平台20.00，代理商16.00，一级4.00 |
| 有一级+二级分销员 | 同上+二级5% | 平台20.00，代理商14.00，一级4.00，二级2.00 |
| 利润为0 | 实付=成本 | 所有人佣金0.00 |
| 极小利润 | 利润0.01元 | 四舍五入，不产生负数 |
| 含小数利润 | 利润37.20x10% | 3.72元（精确到分） |
| 全额退款 | 已完成订单退款 | 各角色产生冲抵记录(-XX元) |
| 部分退款 | 实付100退40 | 按新利润重算佣金 |
| 佣金已提现后退款 | 代理商已提走佣金 | 产生欠款记录，下笔扣回 |
| 比例总和>100% | 平台60%+代理商50% | 保存失败，提示错误 |
| 分销员比例>代理商 | 一级+二级>代理商比例 | 保存被拦截 |
| CPS佣金导入 | Excel导入佣金 | 直接按比例分，不扣成本 |
| 比例为0% | 某角色比例设为0 | 该角色不参与分佣，金额为0 |
| 比例含小数 | 如8.5% | 允许（精度待确认Q18） |
| 利润为负 | 投入>实付 | 后端校验拦截，不应出现 |

#### 各业务线分佣差异验证

| 业务线 | 分佣基数 | 验证要点 |
|--------|---------|---------|
| 餐饮扫码（模式一） | 实付金额 - 商家结算金额 | 折扣计算准确性 |
| 餐饮人工辅助（模式二） | 原价和折扣差额 | 资金未过平台也要算佣 |
| 虚拟商品（券/充值/电影） | API返回佣金 | API回传金额准确性 |
| CPS跳转（外卖红包/打车/家电） | Excel导入佣金 | 不扣成本直接分 |
| 购物返利 | 联盟订单佣金 | 定期同步匹配准确性 |

### 4.2 餐饮折扣（核心复杂模块）

#### 模式一 — 系统直连

| 测试类型 | 测试点 |
|---------|--------|
| 折扣计算 | 100x0.8=80.00、99x0.85=84.15、33x0.85=28.05、0.01x0.8=0.01 |
| 金额输入校验 | 0/负数/超50000/非数字/多小数点/小数超2位/纯小数点 |
| 二维码生成 | 正常生成->15分钟超时->扫码提示"该收款码已失效" |
| 并发扫码 | 两人同时扫同一码->第二人提示"该订单已被支付" |
| 权限控制 | 品牌主账号可修正金额，门店子账号不可修正 |
| 退款-全额 | 用户/商家发起->运营审核->原路退回微信(1-3工作日) |
| 退款-部分 | 退款金额<=实付金额，订单状态"部分退款" |
| 退款校验 | 退款>实付(拦截)、退款=0(拦截)、退款负数(拦截)、重复退款(置灰) |
| 部分退款后再退款 | 退款上限=剩余可退金额 |

#### 模式二 — 人工辅助

**完整链路测试**：

```
用户提交凭证 -> 运营审核通过+输入验证码 -> 验证码推送(订阅消息/短信/订单页)
-> 用户到店出示 -> 商家核销 -> 订单完成 -> 触发分佣
```

| 测试点 | 验证内容 |
|--------|---------|
| 凭证上传-格式 | JPG/PNG通过，PDF拒绝提示"仅支持图片格式" |
| 凭证上传-大小 | <=10MB通过，>10MB提示"图片大小不能超过10MB" |
| 凭证上传-数量 | 支持多张，最多5张（待确认Q7） |
| 凭证上传-操作 | 支持预览大图、支持删除重新选择 |
| 提交校验 | 未输金额/金额0或负/未上传凭证->各有对应提示 |
| 审核-驳回 | 必须填写理由，空理由提交被拦截 |
| 审核-通过 | 必须填写验证码，空验证码拦截 |
| 防重复审核 | 审核通过/驳回后按钮置灰不可点 |
| 多运营并发审核 | 同一订单只能被一人审核 |
| 驳回后重新提交 | 是否保留原信息供修改 |
| 验证码推送 | 优先订阅消息->短信->订单详情页兜底 |
| 验证码推送时效 | <1分钟 |
| 推送失败处理 | 提示运营，验证码仍可在订单详情页查看 |
| 验证码核销-正确 | 核销成功，订单"已完成" |
| 验证码核销-错误 | 提示"验证码错误，请重新输入" |
| 验证码核销-过期 | 超48小时提示"验证码已过期"（待确认Q6） |
| 验证码防暴力破解 | 连续5次错误锁定15分钟 |
| 验证码唯一性 | 每个订单验证码唯一，已核销不可再用 |

#### 商户录入与审核

| 测试点 | 验证内容 |
|--------|---------|
| 必填校验 | 商家名称/地址/联系电话/折扣不能为空 |
| 手机号格式 | 11位手机号格式校验 |
| 折扣范围 | 1折(最低)-9.9折(最高)，0.9折/10折边界 |
| 审核流程 | 待审核->通过(前端可见)/驳回(前端不展示+通知) |
| 同名商家 | 是否允许重复录入 |

### 4.3 订单状态机

#### 合法流转路径验证

**虚拟商品类（外卖券/充值/电影票）**：
```
WAIT_PAY(待支付) --超时--> 已关闭
    |
    | 支付成功
    v
DELIVERING(发货中) --发货成功--> COMPLETED(已完成) [不可退款]
    |
    | 发货失败
    v
FAIL(失败) --重试成功--> COMPLETED
    |
    | 退款
    v
REFUNDED(已退款)
```

**餐饮折扣类（扫码支付-模式一）**：
```
WAIT_PAY(待支付) --> 支付成功 --> COMPLETED(已完成) [保留退款]
    |                                |
    | 超时                            | 退款
    v                                v
  已关闭                          REFUNDED(已退款)
```

**餐饮折扣类（人工辅助-模式二）**：
```
PENDING_AUDIT(待审核) --驳回--> 用户重新上传 --> PENDING_AUDIT
    |
    | 通过+输入验证码
    v
COMPLETED(已完成/验证码已下发)
```

#### 非法流转拦截测试

| 非法操作 | 预期 |
|---------|------|
| COMPLETED直接跳回WAIT_PAY | 拦截 |
| REFUNDED再次退款 | 退款按钮不可见/置灰 |
| 已关闭订单重新支付 | 不可操作 |
| FAIL状态下同时重试和退款 | 互斥（重试中不能退款） |
| 通过API绕过前端直接请求虚拟商品退款 | 后端拦截拒绝 |

#### 退款权限验证

| 订单类型 | 退款权限 |
|----------|---------|
| 虚拟商品(COMPLETED) | **无**退款按钮 |
| 虚拟商品(FAIL) | 有退款按钮 |
| 餐饮扫码 | **有**退款按钮，需填退款原因 |
| 已退款订单 | 不可重复退款 |

#### 前端交互验证

| 要求 | 验证内容 |
|------|---------|
| 下单确认页 | 红色醒目字体"支付后不退款"提示 |
| 勾选框 | "我已阅读并同意"未勾选->支付按钮不可点击 |
| 已完成订单(虚拟商品) | 隐藏"申请退款"按钮 |
| 支付成功页 | 直接展示结果（卡密/充值状态/取票码） |

## 五、安全测试策略

| 安全项 | 测试方法 | 预期结果 | 工具 |
|--------|---------|---------|------|
| 支付金额防篡改 | 抓包修改支付金额参数 | 后端拦截，支付失败 | Charles/Fiddler |
| 越权访问 | 修改请求中订单ID/门店ID | 返回403/无权限 | Postman |
| 虚拟商品退款拦截 | 绕过前端直接调退款API | 后端拒绝 | Postman |
| XSS防护 | 输入框注入`<script>alert(1)</script>` | 输出转义 | 手动 |
| 验证码暴力破解 | 连续5次错误输入 | 锁定15分钟 | 脚本模拟 |
| API鉴权 | 无token/过期token请求 | 返回401 | Postman |
| 并发支付 | 两账号同时扫同一二维码 | 只成功一笔 | JMeter |
| 数据脱敏 | 页面检查手机号显示 | 138****8001格式 | 手动检查 |
| SQL注入 | 输入字段注入SQL语句 | 无异常/被过滤 | 手动/SQLMap |
| 重复提交 | 快速双击支付按钮 | 只产生一笔订单 | 手动 |
